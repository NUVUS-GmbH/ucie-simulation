AXI/AoU-inspired transaction model · specification-derived UCIe recovery

Link recovery alone does not determine AXI transaction fate

Under the modeled observation profiles and specification-derived recovery behavior, there exist executions in which a committed and a non-committed non-idempotent transaction are observationally equivalent to the initiator. UCIe link recovery can leave higher-layer transaction fate indeterminate.

The complete AoU 0.8 text was not available to the model-building workspace. AoU packing and credit behavior are explicit abstractions. The cited link-down activation rule is the normative AoU behavior used by the model. This is not a full AoU 0.8 conformance implementation.

What this study claims

  • Transaction-fate ambiguity is reachable in the executable model.
  • Different architectural outcomes can be observationally equivalent under the modeled standardized interfaces.
  • Blind retry of a committed non-idempotent operation can create a duplicate effect.
  • The specific ambiguity remains reachable in the modeled UCIe 3.0 scenarios.

What this study does not claim

  • UCIe is incorrect.
  • Every UCIe implementation exhibits this behavior.
  • UCIe is responsible for defining AXI architectural commit semantics.
  • UCIe 3.0 provides no automotive reliability improvements.
  • The randomized UNKNOWN percentages are real-world failure probabilities.
  • The current model is a full AoU 0.8 conformance implementation.

02 · Research question

After UCIe error recovery, can the AXI initiator always determine whether an outstanding non-idempotent transaction committed?

For the initiator interface modeled here, the answer is no. Once the link is Active again, “the request was accepted” and “no completion arrived” is compatible with a committed operation and with an operation that never reached the target.

The simulator therefore classifies each interrupted transaction as one of three states. The classifier reads initiator-visible facts. It does not read the target’s commit count. The count is ground truth, used afterwards to test whether a label was sound.

COMPLETED

The initiator received an OKAY completion. A completion that was only generated, or only queued, does not count until the initiator has it.

NOT_COMPLETED

The initiator has a positive reason to treat the effect as absent. Under FDI and AXI alone, that is a transaction the manager never handed to the endpoint. A NAK-only history supports this label only when it is latched before the retry buffers are flushed. UCIe does not require that latch.

UNKNOWN

UNKNOWN is the sound classification for the modeled observer when the available information proves neither completion nor non-execution. Both counterexample traces receive this label from FDI and AXI.

OKAY receivedCOMPLETED
Never handed offNOT_COMPLETED
Accepted, no proofUNKNOWN

A real implementation may avoid exposing UNKNOWN by applying an additional system-level containment rule, reset policy, persistent transaction log, transaction identifier, duplicate-suppression mechanism, or device-specific recovery contract. Hiding the label does not necessarily mean the uncertainty disappeared. Resetting the device may contain the safety risk without reconstructing whether the original operation committed.

No standardized UCIe indication modeled in this study identifies the architectural commit state of the associated AXI transaction. FDI reports link state on pl_state_sts. The cited AoU 0.8 §8.3.3 rule returns the activation FSM to DISABLED on link-down. Architectural commit is a target-device effect. It is not a UCIe link-layer field.

03 · Why this matters

A missing completion is not evidence that the command had no effect.

If a command increments a hardware counter, starts DMA, triggers an actuator command, or rings a doorbell, repeating it may not be safe. The model treats those operations, and an accelerator start, as non-idempotent. The printed counterexample is the counter: the committed trace changes it from 7 to 8, then loses the response.

A link-scoped recovery event may affect transaction-fate knowledge for multiple clients sharing that physical transport. In the UCIe 3.0 run ucie3_two_guests_shared_link, two initiators each finish with architectural_commit_count = 1 and classification UNKNOWN, and the modeled link-scoped signals match. The two-guest scenario motivates a separate freedom-from-interference study. It does not by itself establish an ISO 26262 freedom-from-interference violation.

UCIe provides mechanisms that can support automotive reliability, availability, diagnostics, and safety architectures. It does not itself define ISO 26262 safety goals or the complete application-level reaction to every communication fault. The result identifies one decision the surrounding system must make explicitly: how an interrupted non-idempotent MMIO operation is contained when its architectural effect cannot be reconstructed from the available communication status.

04 · System model

One AXI manager, one AoU endpoint pair, one UCIe link, one target.

The simulator is an AXI/AoU-inspired transaction model over specification-derived UCIe recovery behavior. Time is a sequence of protocol events. It is not a PHY and not a cycle-accurate UCIe implementation. The fault is injected on the channel between the adapters. Architectural commit happens at the target, after both the request and the write data have been delivered. That commit point is a device-model assumption. AoU and UCIe do not define it. The completion then has to travel back.

The complete AoU 0.8 text was not available to the model-building workspace. AoU packing and credit behavior are explicit abstractions; the cited link-down activation rule is the normative AoU behavior used by the model. If the complete AoU 0.8 specification is later added to the repository, that statement should be revised only after the implementation is cross-checked against it.

The model is intentionally event-accurate rather than cycle-accurate because the primary property is an observability and reachability property: whether two different architectural outcomes can produce the same observer-visible state. Cycle-accurate modeling would be needed for quantitative real-time claims such as worst-case recovery latency, deadline violations, arbitration effects, or a precise ambiguity duration in nanoseconds.

05 · Key counterexample

Same observation. Different reality.

Two executions are observationally equivalent for an observer when their architectural ground truth differs, but every fact available to that observer is identical.

The recovery path printed for both traces is:

  1. Active
  2. Retrain
  3. LinkError
  4. Recovery
  5. Active

AoU remains enabled across Retrain. FDI link-down is not signaled for Retrain. LinkError returns the activation FSM to DISABLED under the cited AoU 0.8 §8.3.3 rule, flushes retry buffers, and discards the outstanding message. This is the path of these two traces. Other runs end in a transparent retry or a completed response. Counts are in the results.

If the initiating adapter latches retry disposition before the flush, the traces separate. T18 was only NAK’d, and UCIe does not deliver a CRC-invalid flit, so that assumed latch classifies it NOT_COMPLETED. T17 was acknowledged and then lost its response, so it stays UNKNOWN. The latch is an assumption. UCIe flushes retry buffers on this path and does not require the NAK/ACK history to be kept, tied to an AXI id, and shown to software. The cited AoU 0.8 text does not require it either. Safe automatic retry of T17 is no, with or without the latch.

The same observational equivalence is reported for priority sideband plus a mainband loss, and for endpoint reset. In each pair the commit counts differ and profiles 1, 2, and 3 still match. Signal sets.

Emergency Shutdown is not another CRC or replay case. The UCIe 3.0 scenarios show that the same transaction-fate reasoning can arise when communication is destructively interrupted by endpoint or power recovery. Emergency Shutdown has a different system purpose: rapid containment of a severe condition. The study asks a separate post-event question: what can software infer about transactions that were in flight when containment occurred? It does not treat Emergency Shutdown as defective because it does not preserve transaction completion.

06 · UCIe 2.0 vs UCIe 3.0

For this transaction-fate property, the tested UCIe 3.0 mechanisms did not remove the ambiguity.

UCIe 3.0 improves failure handling at the link level. The architectural commit point remains a target-device effect, outside the UCIe status modeled here. The comparison replays one systematic suite and one seeded random suite on both models, then exercises mechanisms that Revision 3.0 adds. A UCIe 2.0 rule is used for the 3.0 model only where the 3.0 text still states it.

For the specific property studied here, reconstructing the architectural fate of an interrupted non-idempotent transaction from the modeled standardized observations, the tested UCIe 3.0 mechanisms did not eliminate the ambiguity found in the UCIe 2.0 model. That is not a statement that UCIe 3.0 is no better than UCIe 2.0. Equality of the UNKNOWN counts, 171 and 171, applies only to this workload and this transaction-fate property. It is not a general comparison of UCIe 2.0 and 3.0 reliability.

In the modeled architecture, transport-level acknowledgement and target architectural commit are distinct events. On the UCIe 3.0 systematic runs, 9 transactions had a transport acknowledgement with architectural_commit_count 0, and 33 transactions had a commit without an initiator completion. Retaining transport ACK/NAK history can improve classification before target acceptance, but it cannot by itself prove the architectural commit state after the request has progressed beyond the transport boundary. UNKNOWN before target acceptance falls from 48.8% (21/43) to 11.6% (5/43) when retry disposition is assumed to be retained. That latch is an assumed implementation enhancement, not a standardized AXI transaction-fate mechanism.

Fast Throttle, runtime recalibration, and runtime link-testing parity are specified not to discard a valid flit by themselves. Those runs complete the write: classification COMPLETED, commit count 1, completion received. They are not new cases in which a lost completion becomes safe to replay.

07 · Simulation method

Ground truth and the initiator’s view are recorded separately.

Each run is a state machine over AXI, AoU, and UCIe phases: local acceptance, packing, transmission, remote reception, target acceptance, architectural commit, response creation, and response delivery. Faults are armed at a chosen phase. The UCIe paths exercised are CRC replay, the retry threshold, Retrain, LinkReset, and LinkError, plus the UCIe 3.0 mechanisms listed above.

The non-idempotent MMIO model commits at the target. The initiator-visible record stores whether AXI was accepted and whether OKAY was delivered. Systematic scenarios cover the phase crossings. A second suite draws 200 randomized injections from seed 1. Both suites are replayed on the UCIe 3.0 rule set.

Ground trutharchitectural_commit_count = 1
Initiatorcompletion_received = false
ResultUNKNOWN

That split is T17. The classifier never consults the commit count. A later check uses the count only to detect a false safe retry or a duplicate commit.

Outstanding-transaction fate after cleanup is a named policy, because the specification text used here does not define the AXI completion for an outstanding transaction. Five policies are compared. Observation profiles restrict what the classifier may read: FDI and AXI; software error registers; standardized management; and, as an explicit assumption, latched retry disposition. 09 · Safety implications

The automotive system has to define a policy for a command whose effect cannot be reconstructed.

UCIe provides mechanisms that can support automotive reliability, availability, diagnostics, and safety architectures. It does not itself define ISO 26262 safety goals or the complete application-level reaction to every communication fault. The result identifies one decision that the automotive system architecture must make explicitly: how an interrupted non-idempotent operation is contained when its architectural effect cannot be reconstructed from the available communication status.

Policy D retries the same logical transaction after the link is up. On the post-commit loss, the initiator is then told COMPLETED, completion_received is true, and architectural_commit_count is 2. The first commit of that scenario moved the counter from 7 to 8. The retry is a second architectural effect of the same increment. That is a simulation result for this policy, not a required UCIe behavior.

  1. No response
  2. Naive interpretation
    Transaction failed
  3. Automatic retry
  4. Original transaction had already committed
  5. Duplicate effect
    Counter 7 → 8, then a second commit

Exactly-once semantics therefore cannot be assumed from link recovery alone. They need an additional contract: transaction sequencing, persistent commit tracking, or duplicate suppression. UNKNOWN is the sound classification for the modeled observer when the available information proves neither completion nor non-execution. It is not a state that must always be passed to an application or a guest. A real system may instead:

  • transition the operation or device into an indeterminate state and escalate to the safety manager,
  • reset or reinitialize a sufficiently large fault-containment region,
  • use an end-to-end exactly-once or duplicate-suppression mechanism.

Any of those can be a valid system-level response. Containment is not the same thing as reconstructing whether the original operation committed. Automatic retry of an interrupted non-idempotent operation is unsafe in this model without end-to-end commit knowledge or duplicate suppression.

A link-scoped recovery event may affect transaction-fate knowledge for multiple clients sharing that physical transport. The same CRC, Retrain, and LinkError status appears, in the equivalence pairs, for a command that committed and for a command that did not. A LinkError invalidates a known success. It does not justify recording the command as known not to have executed. The two-guest run motivates a separate freedom-from-interference study. It does not by itself establish an ISO 26262 freedom-from-interference violation. Determining whether physical-link recovery can produce cross-guest temporal, spatial, or transaction-state interference in a virtual ECU architecture is future work.

10 · Specification interpretation

Link recovery and transaction recovery are different events.

What the specifications provide

  • Link fault detection, including CRC and replay.
  • Retrain when errors cross an implementation-specific threshold.
  • LinkError, including a visible state, partner propagation, and cleanup in which in-flight packets may be dropped.
  • Recovery coordination back to Active, including the sequence-number handshake.
  • Error propagation on FDI. UCIe 3.0 adds further software-visible and management-visible status. Those fields describe the link, the electrical margin, or an emergency or power indication.

What they do not provide in the modeled scenarios

  • A standardized indication, in the UCIe status modeled here, of the associated AXI transaction’s architectural commit state. That state belongs to the target device.
  • End-to-end exactly-once semantics. Those are an upper-layer recovery responsibility when the system requires them.
  • Mandatory transaction commit logging.
  • Duplicate suppression across recovery.
  • A deterministic classification of every interrupted transaction from link status alone.

This study does not claim that UCIe is incorrect. It identifies a cross-layer recovery gap between link-level recovery semantics and transaction-level architectural knowledge.

UCIe 3.0 §10.3.4, as used by the model, still says the adapter and PHY do not guarantee quiescence of protocol transactions. The investigated UCIe status and management information describes link, transport, electrical, or emergency state. It does not provide the modeled initiator with a standardized AXI architectural-commit indication.

The model identifies an integration ambiguity whose outcome depends on retry-state handling across Retrain. Preserving retry state ends the unacknowledged-response case as COMPLETED with commit count 1. Reinitializing it, which is what §3.8 describes for the IDLE-handshake retry variables, ends as UNKNOWN with commit count 1 and a deadlock flag. The study does not treat that difference as a confirmed normative defect. Separately, a write response already queued in the initiating AoU and not yet accepted on AXI is UNKNOWN under policy A and COMPLETED under policy B, both with commit count 1. Behavior of that queued response is not determined by the modeled UCIe interface. The report calls it an integration choice, not a detected coding bug.

11 · Limitations

What this study can and cannot be used to claim.

  • The simulation is an abstract protocol model, not a silicon implementation. It is intentionally event-accurate. Cycle-accurate modeling would be required before any claim about recovery latency or deadline miss.
  • The complete AoU 0.8 text was not available to the model-building workspace. This is not a full AoU 0.8 conformance implementation. AoU packing and credit behavior are explicit abstractions. The cited §8.3.3 link-down rule is the normative AoU behavior used by the model.
  • Some behavior is an integration choice or a named policy, because the modeled UCIe interface does not determine the AXI completion.
  • Randomized percentages are a fault-workload observation at seed 1. They are not field failure probabilities.
  • Reachability is the scientific conclusion. The rates are not.
  • The study does not prove that every UCIe implementation exhibits this behavior.
  • The ambiguity is reachable under the modeled, specification-derived recovery behavior and the stated device assumptions.
  • UCIe link behavior and target architectural-commit semantics are modeled at different layers. Commit is what the target device does. Observation is what the initiator can read. The surrounding system owns the recovery contract above the link.

Modeling limits, parameters, and the device-commit assumption.

13 · Context

The general phenomenon is known. The contribution is the boundary this model executes.

The general request-executed / response-lost ambiguity is a known distributed-systems and exactly-once-processing problem. The contribution of this study is not the discovery of that general phenomenon.

To our knowledge, the work established by this repository is narrower. It applies that phenomenon to the AXI/AoU–UCIe boundary, constructs executable fault traces, separates architectural ground truth from standardized observer-visible state, demonstrates duplicate execution under blind replay, compares equivalent UCIe 2.0 and UCIe 3.0 recovery scenarios, and frames the consequence for automotive virtualization. A proper literature review would be required before any stronger novelty claim.

14 · Open questions

Questions this study does not answer.

These are future research questions. UCIe 3D is not part of the UCIe 2.0 and UCIe 3.0 simulation. No 3D result is mixed into the counts above.

  1. Which layer should own transaction-fate recovery: AoU, the device protocol, the hypervisor, the safety manager, or the application?
  2. Which non-idempotent MMIO classes may be safely retried after destructive recovery?
  3. Can persistent transaction IDs or duplicate suppression provide exactly-once behavior across LinkError or reset?
  4. How should multiple virtual ECUs sharing one physical UCIe link preserve freedom from interference during recovery?
  5. What are the worst-case fault-detection and recovery latencies for safety-critical traffic? The present model is event-accurate and does not answer that in nanoseconds.
  6. How do UCIe 3.0 Priority Sideband, Fast Throttle, Emergency Shutdown, and runtime recalibration interact with automotive safety-state transitions?
  7. Does UCIe 3D require a different end-to-end integrity and transaction-recovery model when adapter-level CRC and replay are absent or optional for the selected architecture?

15 · Conclusion

Restoring the link and reconstructing the command are different problems.

Under the modeled recovery scenarios, UCIe 2.0 and UCIe 3.0 can restore link operation without necessarily providing the modeled AXI initiator enough standardized information to reconstruct the architectural fate of every outstanding non-idempotent operation.

This is not a claim that UCIe is incorrect. It identifies a cross-layer integration responsibility: a safety-critical system that requires deterministic transaction recovery must provide an additional contract above or around link recovery.

For automotive virtualization, the relevant safety question is therefore not only whether the physical link recovered, but whether the system has a defined and safe policy for commands whose execution state remains indeterminate.

UCIe provides robust mechanisms for detecting, reporting, and recovering from communication faults. The study shows that restoring communication and reconstructing the architectural fate of an interrupted higher-layer operation are different problems. A safety-critical system must define the latter explicitly.
