02 · Research question

After UCIe error recovery, can the AXI initiator always determine whether an outstanding non-idempotent transaction committed?

For the initiator interface modeled here, the answer is no. Once the link is Active again, “the request was accepted” and “no completion arrived” is compatible with a committed operation and with an operation that never reached the target.

The simulator therefore classifies each interrupted transaction as one of three states. The classifier reads initiator-visible facts. It does not read the target’s commit count. The count is ground truth, used afterwards to test whether a label was sound.

COMPLETED

The initiator received an OKAY completion. A completion that was only generated, or only queued, does not count until the initiator has it.

NOT_COMPLETED

The initiator has a positive reason to treat the effect as absent. Under FDI and AXI alone, that is a transaction the manager never handed to the endpoint. A NAK-only history supports this label only when it is latched before the retry buffers are flushed. UCIe does not require that latch.

UNKNOWN

The transaction was accepted and no completion arrived, and standardized status does not prove that the effect was absent. Both counterexample traces receive this label from FDI and AXI.

Never handed offNOT_COMPLETED
Accepted, no proofUNKNOWN

FDI reports link state on pl_state_sts. The cited AoU 0.8 §8.3.3 rule returns the activation FSM to DISABLED on link-down. Neither interface names the outstanding AXI transaction that had reached architectural commit.

03 · Why this matters

A missing completion is not evidence that the command had no effect.

If a command increments a hardware counter, starts DMA, triggers an actuator command, or rings a doorbell, repeating it may not be safe. The model treats those operations, and an accelerator start, as non-idempotent. The printed counterexample is the counter: the committed trace changes it from 7 to 8, then loses the response.

The same gap appears where a chiplet shares a link across clients. In the UCIe 3.0 run ucie3_two_guests_shared_link, two initiators each finish with architectural_commit_count = 1 and classification UNKNOWN. UCIe status is link-scoped. It does not say which guest command already took effect.

For a virtual ECU, the question after the link is healthy again is what it knows about the last safety-relevant command. A Level-4 platform that keeps a function available across a link fault still has to answer that question before it reissues MMIO to an actuator, a DMA engine, or a shared accelerator. The comparison’s automotive reading is that the sound state is UNKNOWN unless a completion was already delivered.

04 · System model

One AXI manager, one AoU endpoint pair, one UCIe link, one target.

The simulator is a discrete-event model of that stack. Time is a sequence of protocol events. It is not a PHY and not a cycle-accurate UCIe implementation. The fault is injected on the channel between the adapters. Architectural commit happens at the target, after both the request and the write data have been delivered. The completion then has to travel back.

AoU remains enabled across Retrain. FDI link-down is not signaled for Retrain. LinkError returns the activation FSM to DISABLED under the cited AoU 0.8 §8.3.3 rule, flushes retry buffers, and discards the outstanding message. This is the path of these two traces. Other runs end in a transparent retry or a completed response. Counts are in the results.

If the initiating adapter latches retry disposition before the flush, the traces separate. T18 was only NAK’d, and UCIe does not deliver a CRC-invalid flit, so that assumed latch classifies it NOT_COMPLETED. T17 was acknowledged and then lost its response, so it stays UNKNOWN. The latch is an assumption. UCIe flushes retry buffers on this path and does not require the NAK/ACK history to be kept, tied to an AXI id, and shown to software. The cited AoU 0.8 text does not require it either. Safe automatic retry of T17 is no, with or without the latch.

The same observational equivalence is reported for three UCIe 3.0-only pairs: Emergency Shutdown, priority sideband plus a mainband loss, and endpoint reset. In each pair the commit counts differ and profiles 1, 2, and 3 still match. Signal sets.

06 · UCIe 2.0 vs UCIe 3.0

UCIe 3.0 improves failure handling at the link level. The architectural commit point remains outside the standardized recovery semantics.

The comparison replays one systematic suite and one seeded random suite on both models, then exercises mechanisms that Revision 3.0 adds. A UCIe 2.0 rule is used for the 3.0 model only where the 3.0 text still states it. None of the modeled mechanisms is class F: none tells the initiator the architectural result.

On the UCIe 3.0 systematic runs, 9 transactions had a transport acknowledgement with architectural_commit_count 0, and 33 transactions had a commit without an initiator completion. Transport acknowledgement is still not architectural commit.

Fast Throttle, runtime recalibration, and runtime link-testing parity are specified not to discard a valid flit by themselves. Those runs complete the write: classification COMPLETED, commit count 1, completion received. They are not new cases in which a lost completion becomes safe to replay.

07 · Simulation method

Ground truth and the initiator’s view are recorded separately.

Each run is a state machine over AXI, AoU, and UCIe phases: local acceptance, packing, transmission, remote reception, target acceptance, architectural commit, response creation, and response delivery. Faults are armed at a chosen phase. The UCIe paths exercised are CRC replay, the retry threshold, Retrain, LinkReset, and LinkError, plus the UCIe 3.0 mechanisms listed above.

The non-idempotent MMIO model commits at the target. The initiator-visible record stores whether AXI was accepted and whether OKAY was delivered. Systematic scenarios cover the phase crossings. A second suite draws 200 randomized injections from seed 1. Both suites are replayed on the UCIe 3.0 rule set.

Initiatorcompletion_received = false
ResultUNKNOWN

That split is T17. The classifier never consults the commit count. A later check uses the count only to detect a false safe retry or a duplicate commit.

Outstanding-transaction fate after cleanup is a named policy, because the specification text used here does not define the AXI completion for an outstanding transaction. Five policies are compared. Observation profiles restrict what the classifier may read: FDI and AXI; software error registers; standardized management; and, as an explicit assumption, latched retry disposition. 09 · Safety implications

Uncertainty becomes a safety issue when recovery assumes failure.

Policy D retries the same logical transaction after the link is up. On the post-commit loss, the initiator is then told COMPLETED, completion_received is true, and architectural_commit_count is 2. The first commit of that scenario moved the counter from 7 to 8. The retry is a second architectural effect of the same increment.

  1. No response
  2. Naive interpretation
    Transaction failed
  3. Automatic retry
  4. Original transaction had already committed
  5. Duplicate effect
    Counter 7 → 8, then a second commit

Exactly-once semantics therefore cannot be assumed from link recovery. They need additional transaction sequencing, persistent commit tracking, or duplicate suppression. UNKNOWN remains a necessary transaction state for the modeled scenarios. Automatic retry of an interrupted non-idempotent operation is unsafe without end-to-end commit knowledge or duplicate suppression.

The comparison applies that to virtualization. UCIe 3.0 error signaling cannot be mapped directly to a guest-visible transaction failure: the same CRC, Retrain, and LinkError status appears for a command that committed and for a command that did not. A LinkError invalidates a known success. It does not justify recording the command as known not to have executed. Several guests on one link are not isolated, for retrospective fate, by a physical link fault.

10 · Specification interpretation

Link recovery and transaction recovery are different events.

What the specifications provide

  • Link fault detection, including CRC and replay.
  • Retrain when errors cross an implementation-specific threshold.
  • LinkError, including a visible state, partner propagation, and cleanup in which in-flight packets may be dropped.
  • Recovery coordination back to Active, including the sequence-number handshake.
  • Error propagation on FDI. UCIe 3.0 adds further software-visible and management-visible status. Those fields describe the link, the electrical margin, or an emergency or power indication.

What they do not provide in the modeled scenarios

  • AXI architectural commit knowledge.
  • End-to-end exactly-once semantics.
  • Mandatory transaction commit logging.
  • Duplicate suppression across recovery.
  • A deterministic classification of every interrupted transaction.

This study does not claim that UCIe is incorrect. It identifies a cross-layer recovery gap between link-level recovery semantics and transaction-level architectural knowledge.

UCIe 3.0 §10.3.4, as used by the model, still says the adapter and PHY do not guarantee quiescence of protocol transactions. Two recorded integration choices sit in that gap. Preserving retry state across Retrain ends the unacknowledged-response case as COMPLETED with commit count 1. Reinitializing it, which is what §3.8 describes for the IDLE-handshake retry variables, ends as UNKNOWN with commit count 1 and a deadlock flag. Separately, a write response already queued in the initiating AoU and not yet accepted on AXI is UNKNOWN under policy A and COMPLETED under policy B, both with commit count 1. The report calls that an integration choice, not a detected coding bug.

11 · Limitations

What this study can and cannot be used to claim.

  • The simulation is an abstract protocol model, not a silicon implementation.
  • AoU 0.8 is under development. The AoU 0.8 specification text is not in this workspace. The normative AoU rule used here is the publicly cited §8.3.3 link-down behavior.
  • Some behavior is implementation-defined and modeled as explicit policy.
  • Randomized percentages depend on the fault workload and seed.
  • Reachability results are stronger than statistical rates.
  • The study does not prove that every implementation will exhibit the same outcome.
  • The study shows that the ambiguity is reachable under the modeled, specification-consistent assumptions.
  • UCIe link behavior and AXI architectural commit semantics are modeled at different abstraction levels.

13 · Conclusion

UCIe 2.0 and UCIe 3.0 can both recover from link-level faults, but neither guarantees that an AXI initiator can reconstruct the architectural fate of every outstanding non-idempotent transaction.

For safety-critical virtualization, interrupted transactions must therefore be modeled as potentially indeterminate unless an additional end-to-end recovery mechanism exists.
